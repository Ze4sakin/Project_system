## 三、新发现的回归缺陷

### R-1【严重·本轮新引入】「只改标题」会静默改写状态/进度，7 组边界组合中 4 组被改

**现象** 任务处于「已取消/100」「阻塞/100」「已完成/60」「进行中/100」这些由用户**显式选择**造出来的组合时，用户只改了标题保存，弹窗关闭、toast 提示"任务已更新"，但状态和进度被静默改掉。其中「阻塞/100」一组还会把用户填的阻塞原因**清空**。

**复现步骤**（任取一组，全程 UI，无 Store 调用）
1. 计划页 → 新增任务 → 状态下拉选「已取消」、进度填 `100` → 创建（此组合可通过场景 2 正常产生）
2. 点该行【编辑】→ **只在标题末尾加一个字** → 点保存
3. 期望：`已取消 / 100`
4. 实际：`已完成 / 100`（被静默"复活"成已完成）

**证据**（页面内断言原始输出）
```
FAIL  只改标题：已取消/100 状态/进度不得变化
        前置={"status":"已取消","progress":100}   改标题后={"status":"已完成","progress":100}
FAIL  只改标题：阻塞/100 状态/进度不得变化
        前置={"status":"阻塞","progress":100,"reason":"等接口"}
        改标题后={"status":"已完成","progress":100,"reason":""}      ← 阻塞原因被清空
FAIL  只改标题：已完成/60 状态/进度不得变化
        前置={"status":"已完成","progress":60}    改标题后={"status":"已完成","progress":100}   ← 用户填的 60% 被抹掉
FAIL  只改标题：进行中/100 状态/进度不得变化
        前置={"status":"进行中","progress":100}   改标题后={"status":"已完成","progress":100}
```
对照：`已取消/30`、`阻塞/50`、`未开始/0` 三组**通过**（不变），说明问题只在「进度 ≥ 100」或「状态=已完成」的组合上触发。

**定位线索** `js/store.js` L442-465 `applyStatusProgress()` 第 3 步：
```js
// 3) 状态没被动过 → 允许在「进度」与「已完成」之间做必要的一致性推导
if (target.progress >= 100) target.status = '已完成';
else if (patch.status === '已完成') target.progress = 100;
```
问题：第 3 步只判断了「状态没变」，**没判断「进度也没变」**。而表单提交时 `status` 和 `progress` 两个字段**永远会带上原值**，所以"只改标题"也会走完第 3 步，把推导当成用户意图执行。

**为什么这一条必须修**
1. 直接违反你本轮下发的回归要求第 2 条；
2. 而且这是**自相矛盾**：场景 6 要求「已完成/60」成为合法状态，但任何一次编辑都会把它抹成 100；场景 2 要求「已取消/100」合法，但改名就变回已完成；
3. 阻塞原因丢失是**不可恢复的数据丢失**（用户要重填）。

**修复建议**：第 3 步前先记 `baseProgress`（改前进度），只有 `Number(patch.progress) !== baseProgress` 时才做进度→状态的推导；状态推导同样只在 `patch.status !== baseStatus` 时做。即两条推导都必须是"用户真的动了那个字段"才触发。
